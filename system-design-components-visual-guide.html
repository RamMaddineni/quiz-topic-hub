6 COMPONENTS

Do not memorize “component → benefit” as a pair of words. Build the causal chain: what is going wrong → what new mechanism is introduced → why that mechanism helps → what the mechanism does not solve.

1

Load balancer: distribute incoming requests

A load balancer is a front door in front of multiple application servers. It receives a client connection or request, selects a backend that should be able to serve it, forwards the request, and returns the backend’s response.

One load balancer: fragile entry point

Users → Only load balancer
failed ✕ → App A ✓ App B ✓ App C ✓

Result: all application servers are healthy, but users have no working path to reach them.

Redundant load-balancing layer

Users → LB A failed ✕ LB B healthy ✓ → App A ✓ App B ✓ App C ✓

Result: the stable service endpoint can still route new traffic through LB B.

Follow one request

The user calls one public service address. The load balancer checks its healthy-backend list, chooses App B, and forwards the request. On the next request it may choose App A. This prevents one server from building a long queue while other servers are idle.

What “the balancer needs redundancy” means

If there is only one load-balancer machine, it becomes a single point of failure. Production systems therefore run multiple load-balancer instances, ideally in separate failure domains such as availability zones, with the same routing configuration.

Who balances the load balancers?

You should not place one ordinary machine in front of them, because that only moves the single point of failure. A managed cloud load balancer usually exposes one logical endpoint while the provider runs many internal nodes. Self-managed designs can publish multiple IP addresses through DNS or use a virtual/anycast address that can reach a healthy balancer.

What it does not guarantee

It cannot create CPU or memory. If every backend is saturated, distributing traffic more evenly is not enough—you must add capacity or reduce work. Bad health checks can also remove a healthy server or keep sending traffic to a server that is alive but unable to serve real requests.

Decision rule: use a load balancer when multiple interchangeable backends exist and requests need distribution or failover. In an interview, say whether the balancing layer itself is highly available; do not draw one magical box and assume it can never fail.

2

Cache: reuse a result instead of repeating expensive work

A cache stores a recently fetched or computed value under a key. Future requests can return that stored value without repeating the slower database query, API call, or computation.

Before the cache

Suppose 10,000 users request the same product. Without caching, the application may execute the same database join 10,000 times. The database repeats work even though the answer changes only occasionally.

Follow one cache-aside read

The app asks the cache for product:42. A hit returns the value immediately. A miss makes the app read the database, return the answer, and place a copy in the cache for later requests.

Why it helps

Most hits avoid the slow source, so user latency and database load fall together. This works only when requests reuse values. If almost every request asks for unique data, the hit rate stays low and the cache adds complexity without removing much work.

New failure modes

The cached copy can become stale after the database changes. Many simultaneous misses for one expired hot key can create a stampede that overloads the database. The design needs an expiry, invalidation, refresh, and source-failure policy.

Decision rule: cache when the same expensive result is read repeatedly and the business can state how stale it may be. Measure hit rate; “reads are slow” alone is not enough justification.

3

Partitioning / sharding: split data ownership

Partitioning places different subsets of the data on different owners. Each shard is responsible for only part of the key space, so storage and work can grow beyond one database machine.

Follow one request

With four shards, a router might hash account_id to choose an owner. Account 123 always routes to shard 3. That shard stores and processes account 123’s data; the other shards own different accounts.

Why it helps

Four owners can provide more total storage and parallel write throughput than one owner. A good partition key also keeps data commonly queried together on one shard, avoiding network calls to every database.

Hot shards

Distribution fails when one key or range receives most traffic. For example, partitioning by country can overload the India shard while other shards are idle. Adding empty shards does not help until the ownership rule can distribute that hot data.

Cross-shard work

A query spanning all users must fan out to many shards and merge results. A transaction touching two owners needs coordination such as a distributed transaction—or a redesigned workflow. Partitioning alone also does not make a failed shard’s data available; that shard needs replication.

Decision rule: partition when one data owner is reaching a real storage or write ceiling and you have a key that distributes load while preserving important access locality.

4

Replication: keep additional copies of the same data

Replication differs from partitioning: a partition owns a different subset, while a replica holds another copy of that subset. Replicas are used for failover, read scaling, or both.

Follow one write

A client writes to the primary or current leader. That node records the change and sends it to replica nodes. Depending on the consistency contract, the system may acknowledge after the leader writes, after a quorum confirms, or after every required replica confirms.

Read scale and failover

Read-only requests may be routed to replicas, reducing pressure on the primary. If the primary fails, an eligible replica can be promoted. Promotion needs detection and coordination so two nodes do not both act as leader with conflicting state.

Replication lag

Copies are not updated at the same physical instant. A user may write a new profile name to the leader and immediately read the old name from a lagging replica. Read-your-writes or strong reads need routing or coordination that proves the selected copy is current enough.

What it does not solve

Adding read replicas does not automatically multiply the write capacity for one heavily updated key, because copies still need the write. Multi-writer replication adds conflict resolution and coordination rather than removing the consistency problem.

Decision rule: replicate when you need another copy to serve reads or survive a node failure, and explicitly state what staleness is acceptable and how failover chooses one safe writer.

5

Message queue: persist work between producer and consumer

A producer writes a message describing work; a consumer processes it later. They no longer need to run at the same speed or be healthy at the same moment.

Follow one job

A video service durably stores an upload, places “generate thumbnails for video 91” in a queue, and returns accepted / processing. A worker later receives the message, generates the files, and records completion.

Why it helps

A burst of 100,000 uploads can wait in durable storage while workers process at a sustainable rate. If workers are briefly down, producers may continue accepting work as long as the queue has capacity and the business tolerates delayed completion.

Accepted is not completed

Fast enqueue latency proves only that the queue accepted the message. If the oldest message has waited two hours, the intake API is available but the business task is severely delayed. Monitor backlog size and oldest-message age.

Retries and duplicates

A worker can finish a side effect and crash before acknowledging the message. The queue may redeliver it, so consumers need idempotency or durable deduplication. Ordering may also be limited to a partition or message group rather than the entire queue.

Decision rule: queue work when the caller does not need the final result immediately, bursts or temporary downstream failures must be buffered, and the product can expose an honest pending/completed state.

6

Batch processing: process many items as one scheduled unit

Batch systems collect or select a large set of records and process them together, often on a schedule or after a size threshold. They optimize total work completed, not the response time of one record.

Follow one batch

At midnight, a job reads the day’s events, groups them, computes aggregates, and writes a report by 6:00 AM. No user request remains open while the job runs; the contract is a morning deadline.

Throughput versus latency

Grouping records can amortize startup, scheduling, and I/O overhead, increasing total records processed per minute. But an event created at 12:01 AM may wait almost 24 hours for the next daily batch, so its individual latency is high.

Queue versus batch

A queue is mainly a transport and buffering boundary between producers and consumers. Batch is an execution strategy that groups many items. They can be combined: queue events during the day, then consume or aggregate them in batches.

What it does not fit

Do not put an interactive action such as payment authorization into a next-day batch when the user needs an immediate answer. Batch failures also require checkpointing, retries, and careful handling so a rerun does not duplicate outputs.

Decision rule: use batch processing when the work is large and noninteractive, efficiency matters more than per-item freshness, and the business provides a completion deadline rather than a millisecond response target.

Compose paths without mixing guarantees

One product may use several components, but each affects only its own boundary. Trace a synchronous request, a data operation, and background work independently.
