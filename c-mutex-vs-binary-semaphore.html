Mutex vs binary semaphore in C: owned key versus signal token.

Both can make only one thread move at a time. That is the confusing part. The difference is the promise underneath: a mutex has an owner and protects shared state; a semaphore has a count and can pass permission from one thread to another.

Scope: the C examples use POSIX threads and unnamed POSIX semaphores on Unix-like systems: <pthread.h> and <semaphore.h>. These semaphore functions are POSIX APIs, not part of ISO C itself.
Mutex = one owned key

pthread_mutex_lock() makes the calling thread the owner. That owner must call pthread_mutex_unlock(). Use it around a critical section that protects an invariant.

Semaphore = a bowl of tokens

sem_wait() takes one token; sem_post() adds one. There is no owner, so a producer may post a token that wakes a different consumer.

Remember: a mutex asks “Which thread owns this lock?” A semaphore asks “How many permits are available?” Same one-at-a-time result is possible; the ownership contract is different.

Locking versus signaling: locking says, “I am entering shared state; keep everyone else out until I finish.” Signaling says, “Something happened; one waiting operation may continue.” In this lesson, signal means synchronization notification—not a Unix signal such as SIGUSR1.

Replace the story with exact state

A primitive becomes easier when every state transition is visible. The biggest POSIX C surprise is that sem_t is a counting semaphore; “binary” is how your program agrees to use it.

PRECISE MODEL

pthread_mutex_t

The simple model stores availability plus owner identity.

UNLOCKED
owner = none ⇄ LOCKED
owner = Thread A
  • A locks: unlocked → locked(owner=A); A enters.
  • B locks: A owns it, so B waits.
  • A unlocks: legal; ownership ends.
  • B unlocks A’s mutex: violates the ownership contract.

Binary use of POSIX sem_t

Your design intends the count to stay 0 or 1.

COUNT = 0
no permit ⇄ COUNT = 1
one permit
  • Wait at 1: 1 → 0; caller proceeds.
  • Wait at 0: caller blocks.
  • Post at 0: wake one waiter or store one permit.
  • Post at 1: POSIX normally makes the count 2.
Critical C-specific fact: sem_init(&s, 0, 1) sets only the initial count. There is no “maximum = 1” argument. If buggy code calls sem_post() while the count is already 1, the count can become 2, up to SEM_VALUE_MAX. Therefore a “binary POSIX semaphore” is a counting semaphore kept binary by correct program discipline.

Do not repair that with sem_getvalue()

Checking “is the count already 1?” and then posting is a race: another thread can change the semaphore between the check and the post. sem_getvalue() is a snapshot for observation, not an atomic max-one guard.

Mutex behavior depends on its type

With PTHREAD_MUTEX_ERRORCHECK, a non-owner unlock returns EPERM. With PTHREAD_MUTEX_NORMAL, a non-owner unlock has undefined behavior. Ownership is still the contract; error-checking changes detection, not the rule.

Who releases? The owner thread calls pthread_mutex_unlock(). Any thread with access may call sem_post().

Can producer wake consumer? Not by unlocking the consumer’s mutex; the producer is not its owner. Yes. Consumer waits; producer posts.
Mutual exclusion? Yes; that is the primary contract. Yes only while every path obeys successful-wait → one-post pairing.
Wrong release Error-check mutex returns EPERM; normal mutex gives undefined behavior. May silently add a permit and allow two threads inside.
Return convention Most pthread functions return an error number directly; do not read errno for that result. sem_* functions generally return -1 and set errno.
Interrupted wait pthread_mutex_lock() does not return EINTR. sem_wait() may return -1 with errno == EINTR; retry if interruption is not your stop condition.
Owner dies A robust mutex can report EOWNERDEAD; the new owner must repair state and call pthread_mutex_consistent(). No owner exists. A missing post can leak the permit and leave waiters blocked.
FIFO fairness? Do not assume first waiter wins unless your target system and scheduling policy guarantee it. Do not build correctness on FIFO waiter order.
Process sharing Requires process-shared attributes and shared memory. pshared != 0 requires shared memory; named semaphores use sem_open().

The critical section is free

    Ten practical end-to-end cases

    Every trace follows starting condition → operation → state change → consequence → rule. This is where definitions become debugging skill.

    10 CASES
    Case 1 · Correct mutex

    Two withdrawals, one balance

    The invariant is “balance never goes below zero.” Reading, checking, and writing must be one critical section.

    1. A locks; owner becomes A.
    2. A reads ₹1,000 and approves ₹700.
    3. B tries to lock and waits.
    4. A writes ₹300 and unlocks.
    5. B locks, sees ₹300, rejects ₹500, and unlocks.
    6. Result: the read-check-write invariant stays valid.
    Case 2 · Wrong owner

    B unlocks A’s mutex

    Unlock means “I am the owner and I finished.” B cannot say that for A.

    1. A locks an error-check mutex.
    2. B calls pthread_mutex_unlock().
    3. The call returns EPERM; A remains responsible.
    4. A completes and unlocks correctly.
    5. With a normal mutex, B’s call would be undefined behavior—not a safe shortcut.
    6. Rule: use a signaling primitive for notification.
    Case 3 · Correct signal

    Producer says “data is ready”

    The semaphore starts at 0 because nothing is ready yet.

    1. Consumer waits at count 0 and blocks.
    2. Producer fully writes the result.
    3. Producer posts, even though it never waited.
    4. Consumer wakes, consumes the permit, and reads the result.
    5. Count is effectively 0 again.
    6. Result: one thread enables a different thread.
    Case 4 · Disciplined gate

    A semaphore imitates one-at-a-time entry

    The semaphore starts at 1. Every successful waiter posts exactly once after leaving.

    1. A waits: 1 → 0, then enters.
    2. B waits at 0 and blocks.
    3. A leaves and posts.
    4. B receives the permit and enters.
    5. At most one is inside while pairing remains correct.
    6. Difference: no owner field enforces who may post.
    Case 5 · Early post

    A wrong thread breaks the gate

    A is still inside when unrelated C posts.

    1. A waits and enters; count becomes 0.
    2. B waits and blocks.
    3. C mistakenly posts without owning or acquiring anything.
    4. B wakes and enters while A is still inside.
    5. Two threads now modify the supposedly protected state.
    6. Lesson: a semaphore gate relies on code discipline.
    Case 6 · Extra post

    “Binary” becomes count 2

    POSIX does not store a max-one setting for an unnamed semaphore.

    1. sem_init(&s, 0, 1) creates count 1.
    2. Buggy code calls sem_post(&s).
    3. The count becomes 2.
    4. A waits and enters: 2 → 1.
    5. B waits and also enters: 1 → 0.
    6. Result: the supposed binary gate admits two.
    Case 7 · EINTR

    A Unix signal interrupts sem_wait()

    An interrupted wait did not acquire a permit.

    1. Consumer blocks in sem_wait().
    2. A signal handler runs.
    3. sem_wait() returns -1 and sets errno = EINTR.
    4. Consumer has no permit and must not post.
    5. If interruption is not a stop request, loop and wait again.
    6. Rule: cleanup depends on successful acquisition.
    Case 8 · Timeout

    A timed wait expires

    sem_timedwait() can return -1 with ETIMEDOUT.

    1. B requests a permit with a deadline.
    2. No permit arrives before the deadline.
    3. B never enters the protected operation.
    4. B must not call sem_post() in cleanup.
    5. Posting would manufacture permission B never received.
    6. Invariant: successful acquisitions = paired releases.
    Case 9 · Owner death

    A robust mutex reports damaged state

    Exclusion and data consistency are different problems.

    1. A owns a robust mutex and dies mid-update.
    2. B locks and receives EOWNERDEAD.
    3. B owns the mutex, but protected data may be inconsistent.
    4. B repairs or rolls back the data.
    5. B calls pthread_mutex_consistent(), then unlocks.
    6. Lesson: gaining the lock does not magically repair state.
    Case 10 · Repeated work

    Every produced item must survive

    A single binary permit cannot store an arbitrary backlog or the items themselves.

    1. Producer creates jobs J1, J2, and J3.
    2. A one-bit signal can only say “something is ready.”
    3. It cannot tell which jobs exist or retain their payloads.
    4. Store jobs in a queue protected by a mutex.
    5. Use a condition variable or counting semaphore to wake consumers.
    6. Decision: data structure first; notification second.

    1 · Protect read-check-write with a mutex

    The same owner locks and unlocks around one invariant.

    static pthread_mutex_t balance_mutex =
    PTHREAD_MUTEX_INITIALIZER;
static long balance = 1000;

bool try_withdraw(long amount)
{
    bool approved = false;
    int rc = pthread_mutex_lock(&balance_mutex);
    if (rc != 0)
        return false; /* report rc in real code */

    if (balance >= amount) {
        balance -= amount;
        approved = true;
    }

    rc = pthread_mutex_unlock(&balance_mutex);
    /* handle rc; pthread functions return the error number */
    return approved;
}
    Keep the whole invariant together: locking only the write is too late; another thread could race between the read, check, and write.

    2 · Signal data readiness with count 0

    One thread publishes; another waits and consumes.

    static sem_t ready;
static int result;

void initialize(void)
{
    if (sem_init(&ready, 0, 0) == -1)
        perror("sem_init");
}

void *producer(void *unused)
{
    result = 42;             /* publish data first */
    if (sem_post(&ready) == -1)
        perror("sem_post");
    return NULL;
}

void *consumer(void *unused)
{
    while (sem_wait(&ready) == -1) {
        if (errno != EINTR) {
            perror("sem_wait");
            return NULL;
        }
    }
    printf("%d\n", result);  /* prints 42 */
    return NULL;
}
    Different actors are intentional: the producer posts without waiting. That is signaling, not unlocking somebody else’s lock.

    3 · Use a semaphore as a disciplined gate

    Track whether acquisition succeeded before cleanup posts.

    int use_one_at_a_time(sem_t *gate)
{
    bool acquired = false;
    int status = -1;

    while (sem_wait(gate) == -1) {
        if (errno != EINTR)
            goto cleanup;
    }
    acquired = true;

    status = update_shared_resource();

cleanup:
    if (acquired && sem_post(gate) == -1) {
        perror("sem_post");
        return -1;
    }
    return status;
}
    C has no automatic finally block: a cleanup label plus an acquired flag makes the release rule explicit on every return path.

    4 · Turn ownership mistakes into EPERM

    An error-check mutex is useful while learning and diagnosing.

    pthread_mutexattr_t attr;
pthread_mutex_t mutex;
int rc;

rc = pthread_mutexattr_init(&attr);
if (rc != 0)
    report_pthread_error(rc);

rc = pthread_mutexattr_settype(
    &attr, PTHREAD_MUTEX_ERRORCHECK);
if (rc != 0)
    report_pthread_error(rc);

rc = pthread_mutex_init(&mutex, &attr);
if (rc != 0)
    report_pthread_error(rc);

/* A non-owner pthread_mutex_unlock(&mutex)
   now returns EPERM. */
    Do not confuse detection with permission: a normal mutex does not permit wrong-owner unlock; its behavior is simply undefined instead of reliably returning EPERM.
    Lifecycle rule: initialize before sharing the object; destroy only after no thread can still lock, wait, post, or use it. Destroying a mutex or semaphore while another thread is using or waiting on it is not cleanup—it is a lifetime bug.

    Choose from the coordination rule

    Begin with what must be true, then select the primitive that expresses that contract.

    DECISION RULE
    Protecting shared state or a multi-step invariant? → Use pthread_mutex_t. Ownership matches “the thread inside must be the thread that unlocks.”
    One thread must wake a different thread? → Use a semaphore starting at 0 when a stored permit is the right meaning. The producer posts; the consumer waits.
    Wait until a predicate over shared state becomes true? → Use a condition variable with a mutex. Re-check the predicate in a loop; the mutex protects the predicate’s data.
    Allow up to N workers or N pooled resources? → Use a counting semaphore initialized to N. The count represents available capacity.
    Need one-at-a-time entry but no cross-thread handoff? → Prefer a mutex. A semaphore initialized to 1 can work, but it discards owner checking and can be over-posted.
    Must every item or event be retained? → Use a queue plus synchronization. A semaphore counts permission; it does not store payloads.

    Say it clearly in an interview

    Lead with ownership and purpose. Then add the POSIX-specific “binary is a convention” detail.

    ARTICULATION

    30-second answer

    “A mutex is an ownership-based lock: the thread that successfully locks it owns it and must unlock it, so I use it to protect a critical section and its invariant. A semaphore is a counter with no owner: wait consumes a permit and post supplies one, so one thread can signal another. Initial count 0 means wait for a signal; initial count 1 can make a one-at-a-time gate. In POSIX C, sem_t is still a counting semaphore—there is no maximum-one argument—so binary behavior depends on never over-posting.”

    Likely follow-ups

    Can a binary semaphore provide mutual exclusion? Yes, if it starts at 1 and every successful wait has exactly one correct post. A mutex is safer when ownership is the desired rule.
    Why not use a mutex for producer-to-consumer signaling? The producer normally does not own the consumer’s mutex, so it cannot legally unlock it. A semaphore intentionally permits cross-thread post/wait.
    What is the 0-versus-1 initial count? 0 means closed until somebody posts. 1 means one wait can succeed immediately.
    What happens on wrong-owner unlock? Error-check and recursive mutexes return EPERM; normal-mutex behavior is undefined. Never depend on the bug being detected.
    What if sem_wait() gets EINTR? No permit was acquired. Retry when appropriate, and do not post in a cleanup path that never acquired.
    Strong interview phrase: “Same possible capacity of one, different ownership contract.” Capacity tells how many may proceed; ownership tells who has the right and duty to release.

    REVISION

    Definition

    Mutex = owner-aware lock. Semaphore = ownerless permit counter.

    Mutex invariant

    The successful locker owns it; that same thread unlocks it.

    Semaphore transitions

    Wait decrements or blocks. Post increments or wakes one waiter.

    Initial count

    0 = wait for signal. 1 = one-at-a-time gate.

    POSIX trap

    sem_t has no max-one setting. An extra post can produce count 2.

    Cleanup rule

    Release only after successful acquisition, except an intentional producer signal.

    1 · What information does a mutex have that a semaphore lacks?

    Owner identity: the thread that successfully locked the mutex has the right and responsibility to unlock it.

    2 · Why does count 0 fit producer-to-consumer signaling?

    The consumer cannot pass before the producer publishes the condition and supplies a permit.

    3 · How can a POSIX semaphore imitate a lock?

    Initialize to 1; wait before entry and post after exit. This works only while all code obeys the pairing discipline.

    4 · Why is “binary” only a convention for sem_t?

    sem_init() accepts an initial value but no maximum value. Posting at count 1 can raise it to 2.

    5 · What does wrong-owner unlock do?

    An error-check mutex returns EPERM. A normal mutex gives undefined behavior. Both mean the program violated the ownership rule.

    6 · Who may call sem_post()?

    Any thread with access to the semaphore. It does not need to be a thread that previously waited.

    7 · Should an interrupted or timed-out waiter post?

    No. It acquired no permit. Posting would manufacture capacity.

    8 · Why not check sem_getvalue() before posting?

    The check and post are not one atomic operation; another thread can change the count between them.

    9 · What should protect a repeated predicate?

    A mutex plus condition variable: the mutex protects the state, and the waiter re-checks the predicate in a loop.

    10 · What should retain every work item?

    A queue that stores the items, combined with a mutex and condition variable or an appropriately paired counting semaphore.

    One final test: if Thread P should do work and then wake Thread C, choose signaling. If Thread P should enter shared state and keep others out until P itself finishes, choose locking. Ask “notification or ownership?” before reaching for an API.
