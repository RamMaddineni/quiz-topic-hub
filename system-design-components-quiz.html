Select from the pressure

Questions 1–6 · choose a component only after the measured problem is explicit

1. Uneven traffic across application servers
Current system
Six identical, stateless application servers can each handle any request. Static network routing currently sends every request to server A.
Observed evidence
Server A stays above 95% CPU and 95% of its requests take 1.8 seconds. Servers B–F stay near 20% CPU and answer in about 120 milliseconds. The database is below 35% utilization.
Required behavior
Use the existing six servers to keep 95% of requests below 300 milliseconds and stop routing to an application server when it fails.
Known constraints
Requests perform similar work and responses are user-specific, so there is no reusable response to cache.

Decision: Which change directly addresses both the uneven routing and failed-server handling described above?

Given facts: Five application servers have spare capacity, one server is overloaded, any server can handle any request, and the database is not the bottleneck.

Reasoning: A load balancer changes the exact decision that is wrong: which application server receives each request. Health checks also let it stop choosing a failed server.

Boundary: The balancer uses existing capacity more evenly; it does not create additional server capacity when all six servers are busy.

2. Repeating the same expensive product read
Current system
Every product-page request runs the same read-only database join. For a given product, the computed result is identical for every visitor.
Observed evidence
The join takes 650 milliseconds and accounts for most database load. Ninety-two percent of traffic is for the same 100 products; application CPU is only 25%.
Required behavior
Return the page within 250 milliseconds. Product data may be stale for at most 30 seconds.
Known constraints
Products change at most once per hour. The write path can delete or replace a stored result when a product changes.

Decision: Which first change uses the repeated work and the written freshness allowance?

Given facts: Many requests need an identical result, the repeated database work dominates latency, and the business explicitly permits up to 30 seconds of staleness.

Reasoning: A cache reuses one computed result instead of paying for the same 650-millisecond join on every request. The invalidation and expiry rules connect cache behavior to the 30-second requirement.

Boundary: Caching does not make data automatically fresh. Without invalidation or a bounded expiry, the stored product result could outlive the allowed staleness.

3. One database has reached its storage and write ceiling
Current system
One database machine stores 8 terabytes of append-only events for 40,000 customer accounts.
Observed evidence
Disk capacity is 92% full and sustained write input/output is at its safe limit. Application servers and network links have spare capacity.
Required behavior
Support four times the current stored data and write rate. Interactive reads must remain fast for one account at a time.
Known constraints
More than 99% of reads and writes concern one account_id; account IDs are well distributed, and interactive cross-account transactions are not required.

Decision: Which data-placement change directly raises both the storage and write ceilings?

Given facts: One machine is limited by both stored bytes and write input/output, while account-scoped access gives a well-distributed routing key.

Reasoning: Partitioning splits data ownership. Each machine stores only some accounts and accepts only those accounts’ writes, so storage and write work scale across machines.

Boundary: Partitioning alone does not create backup copies. Each partition still needs replication if its data must remain available after its owner fails.

4. Read pressure and a single database failure point
Current system
One database contains the complete 600-gigabyte dataset and is the only copy serving the application.
Observed evidence
Read capacity is above 90% during peak hours, write capacity is below 20%, and the dataset still fits comfortably on one machine.
Required behavior
Double read capacity and restore database service within 60 seconds if the current machine fails.
Known constraints
Ordinary reads may be up to two seconds behind the newest write. A monitored failover process is allowed to promote a copy after confirming the old writer is unavailable.

Decision: Which design addresses the measured read pressure and the loss of the only data copy?

Given facts: The dataset fits on one node, writes have headroom, reads are the capacity problem, two seconds of read lag is accepted, and the only current copy is a failure risk.

Reasoning: Replication creates additional copies. Those copies can serve the permitted slightly stale reads, and a controlled promotion can restore writes after the original writer fails.

Boundary: Replicas are not instantaneously current, and safe failover is not automatic merely because copies exist; routing, lag handling, and promotion rules must be designed.

5. Slow thumbnail work blocks a fast upload response
Current system
The upload API stores an original image and then generates three thumbnails before returning to the client. Thumbnail generation takes 4–20 seconds.
Observed evidence
Traffic bursts cause request timeouts. Clients retry timed-out uploads, creating more work while the service is already busy.
Required behavior
Return within 300 milliseconds only after the original image and the thumbnail job are durably accepted. Show “processing,” and finish 95% of thumbnails within two minutes.
Known constraints
The thumbnail is not needed in the upload response. More worker instances can be added when pending work grows.

Decision: Which request flow matches all four written facts?

Given facts: Thumbnail work is slow, the result is not needed immediately, bursts cause timeouts, and the client accepts a processing state after durable intake.

Reasoning: A durable message queue separates the fast acceptance path from slower thumbnail workers. It can hold burst work and lets worker capacity scale independently.

Boundary: The queue does not guarantee the two-minute completion target by itself. Worker throughput and oldest-job age still have to be measured and controlled.

6. A large report has a deadline, not an interactive user
Current system
Finance calculates a ranking from the previous day’s 400 million events. The day’s input closes at midnight.
Observed evidence
Starting and committing work separately for every event wastes significant setup and input/output time.
Required behavior
Publish the complete ranking by 6:00 AM. No consumer needs partial or intermediate rankings.
Known constraints
Compute costs less from midnight to 5:00 AM, and delaying any individual event until that window is acceptable.

Decision: Which execution model meets the deadline while taking advantage of grouped work and the cheaper window?

Given facts: The input closes at midnight, only the final result matters, completion is due at 6:00 AM, and grouped overnight work is cheaper.

Reasoning: Batch processing optimizes total work completed per unit of time by sharing setup and input/output across many records and using the allowed processing window.

Boundary: Batch improves throughput here by accepting delay for each individual event. It is a poor fit when every event needs an immediate result.

Mechanisms and limits

Questions 7–13 · separate what a component changes from what it cannot guarantee

7. A load balancer cannot manufacture backend capacity
Current system
A load balancer already distributes equal-cost requests evenly across ten identical application servers.
Observed evidence
Every server remains above 95% CPU for ten minutes, each server’s request queue grows, and traffic is within 3% of an even split. The database is below 35% utilization.
Required behavior
Handle the current arrival rate without a growing queue and keep 95% of responses below 400 milliseconds.
Known constraints
Responses are personalized and rarely repeat. There is no idle application server to which the balancer could redirect more work.

Decision: Which next action directly addresses the remaining bottleneck?

Given facts: Routing is already even, every backend is saturated, queues are growing, and no unused backend capacity exists.

Reasoning: The balancer has completed its job: it spread work. The system must now process more work per second by adding backend capacity or making each request cheaper.

Boundary: Load balancing improves use of available capacity and routes around failed nodes. It cannot make a saturated fleet perform more computation.

8. A cache and database hold separate versions of a price
Current system
Reads check a cache first. On a miss, the service reads the database and stores that value in the cache with a ten-minute time-to-live (TTL). Database writes do not update or delete the cached entry.
Observed evidence
At 12:00 the cache stores a ₹1,000 price. At 12:01 the database changes to ₹900. Requests continue hitting the existing cache entry.
Required behavior
No customer may see a price more than 30 seconds behind the database.
Known constraints
The service must retain caching because the uncached database read cannot handle peak traffic.

Decision: Which statement accurately describes the current behavior and a change that can satisfy the 30-second limit?

Given facts: Reads stop at the cache, the write path does not touch it, and its ten-minute lifetime exceeds the allowed 30 seconds.

Reasoning: The old entry remains a valid cache hit even after the database changes. Explicit invalidation or update connects writes to cached state; bounded expiry limits damage if that action fails.

Boundary: A shorter TTL lowers the maximum stale period but increases cache misses. The chosen policy must balance freshness against source load.

9. Partitioning and replication change different things
Current system
Design X has four nodes: each node is the only owner of a different quarter of the customer records. Design Y also has four nodes: every node stores the complete customer dataset, and writes are copied from one writer to the others.
Observed evidence
In X, adding nodes can divide storage and write ownership. In Y, another full copy can serve reads or take over after failure, subject to copy lag and failover rules.
Required behavior
Correctly name the mechanisms so a later design can decide whether it needs scale, copies, or both.
Known constraints
No other data-placement behavior should be assumed beyond the two designs described.

Decision: Which description matches Design X and Design Y?

Given facts: X assigns different records to different owners; Y stores the same records on multiple nodes.

Reasoning: Partitioning answers “which node owns this subset?” Replication answers “which additional nodes hold a copy of that owned data?” These choices are independent and are often combined.

Boundary: More nodes alone do not reveal the mechanism. You must inspect whether the nodes divide data or copy it.

10. Partitioning without copies during a node failure
Current system
Customer records are split into eight partitions. Each partition exists on exactly one machine; there are no live replicas or other copies that can serve requests.
Observed evidence
Machine 3 has failed. It was the sole owner of partition 3. Machines 1, 2, and 4–8 remain healthy.
Required behavior
Continue serving every record that is still reachable, and report unavailable records honestly.
Known constraints
The request router knows which partition owns each customer ID and does not require a query to contact every partition.

Decision: What can this system serve before machine 3 is recovered?

Given facts: Seven owners are healthy, partition 3 has one failed owner, no copy exists, and requests can be routed to one partition.

Reasoning: Partitioning can contain the failure to the affected ownership range, so unrelated partitions continue. It cannot serve data for which the only copy is unreachable.

Boundary: Replicating each partition and defining failover is the separate mechanism needed to keep that partition available after its owner fails.

11. An immediate read can reach a replica that has not copied the write
Current system
Profile writes go to one primary database. The primary acknowledges a write before asynchronously copying it to read replicas; “asynchronously” means the copying finishes later. The read router chooses a replica at random.
Observed evidence
Replica lag is normally zero to two seconds. A user changes “Ram” to “Rama” and immediately reads from a replica that still contains “Ram.”
Required behavior
The user who made a change must see that change on their next read. Other users may see profile data up to two seconds late.
Known constraints
Routing every read from every user to the primary would overload it; only the writer’s immediate follow-up reads need the stronger rule.

Decision: Which routing rule provides the stated “see my own write” behavior without strengthening every read?

Given facts: The primary acknowledges before replicas finish copying, random routing can choose a lagging copy, and only the writer’s next read needs to observe the write.

Reasoning: The read must go to a copy known to contain that write. Temporarily routing the writer to the primary, or checking a replication position, establishes that fact.

Boundary: Replication adds read capacity, but asynchronous copies do not by themselves guarantee the newest value. Stronger read rules add routing, waiting, or coordination.

12. Durable queue retry can repeat a completed side effect
Current system
The payment queue uses at-least-once delivery: an unacknowledged message is delivered again. The payment provider supports an idempotency key, meaning repeated calls with the same key return the first result without charging again.
Observed evidence
A worker charges order 817, then crashes before acknowledging the queue message. The queue delivers order 817 to another worker.
Required behavior
Every accepted order must be attempted, but the customer must receive at most one successful charge for one order.
Known constraints
A worker can crash between any two instructions. Changing which worker receives the retry does not change what the first worker already did.

Decision: How should the consumer process the redelivered message?

Given facts: The queue intentionally retries unacknowledged work, the first charge may already have succeeded, and the provider deduplicates calls that reuse one key.

Reasoning: A stable order key makes repeated deliveries represent the same business operation. The second worker can safely ask for the outcome without causing a new charge.

Boundary: A durable queue protects against lost work; it does not automatically provide exactly-once business effects. The consumer and side-effecting service must participate in deduplication.

13. Batch throughput can improve while one record waits longer
Current system
Importing one record opens a database transaction, pays two seconds of setup, performs one millisecond of record work, and commits. The importer repeats that sequence for every record.
Observed evidence
For 1,000 records, setup dominates useful work. One batch can pay the two-second setup once and then perform roughly one second of record work.
Required behavior
Maximize records imported per minute. It is acceptable for a newly arrived record to wait up to one minute before processing begins.
Known constraints
No user is waiting interactively for an individual record, and all 1,000 records use the same operation.

Decision: Why does grouping records improve the stated goal even though an individual record may finish later?

Given facts: Per-operation setup is 2,000 times larger than per-record work, total records per minute is the goal, and one minute of waiting is accepted.

Reasoning: Sharing setup across 1,000 records removes repeated overhead from the total workload, so many more records finish per minute.

Boundary: The gain is throughput, not instant completion. A record can wait for the collection window, the batch to start, and work ahead of it.

Production failure and synthesis

Questions 14–20 · reason through skew, retries, failure points, and composed systems

14. A partition key concentrates most writes on one owner
Current system
Events are partitioned by country. One partition owns India, while three other partitions own groups of less active countries.
Observed evidence
India produces 80% of writes. Its partition stays above 95% disk input/output while the other three remain below 20%; this overloaded owner is a hot partition.
Required behavior
Support four times the current write rate while keeping events for one account easy to query.
Known constraints
Queries are by account_id, not by country. Account IDs are well distributed, and no single account produces more than 0.1% of traffic.

Decision: Which ownership redesign lets additional partitions share the write load?

Given facts: Country creates severe skew, account-scoped queries are the real locality need, and account IDs distribute traffic well.

Reasoning: A partition key decides which owner receives each write. Hashing the account ID creates many routing values, allowing accounts—and therefore writes—to spread across owners.

Boundary: Adding machines changes nothing until ownership can move to them. Repartitioning also requires a migration and routing plan while old and new placements coexist.

15. One money transfer crosses two independent partitions
Current system
Accounts are partitioned by account ID. A database transaction is atomic—both changes happen or neither happens—only when all changes are on one partition.
Observed evidence
A transfer must debit account 10 on partition A and credit account 92 on partition B. A crash can occur after either partition writes.
Required behavior
The transfer must commit both the debit and credit or commit neither. Reporting success while only one side is durable is forbidden.
Known constraints
Transfer pairs are arbitrary, so a partition key cannot place every possible pair together. The business will accept extra latency for correct transfers.

Decision: Which statement is honest about the mechanism required at this partition boundary?

Given facts: The invariant spans two owners, local transactions cover only one owner, arbitrary transfer pairs cannot all be co-located, and partial success is forbidden.

Reasoning: Both partitions need a shared decision. A coordinator can run a protocol such as two-phase commit: first prepare both participants, then issue one commit or abort decision.

Boundary: Cross-partition coordination preserves the invariant but adds network round trips, failure recovery, and possible waiting when a participant or coordinator is unreachable.

16. One cache expiry causes thousands of identical source reads
Current system
A popular homepage result is cached for five minutes. When it expires, any request that misses independently runs the same database query and stores the result.
Observed evidence
At exactly noon the entry expires. Five thousand near-simultaneous requests all miss, run the same query, and push the database above its connection limit.
Required behavior
Keep the database below 70% connection use and keep serving the homepage during refresh.
Known constraints
Only one fresh computation is needed. The previous value may be served for 30 additional seconds while refresh occurs.

Decision: Which refresh rule directly prevents the synchronized miss from multiplying database work?

Given facts: Thousands of requests need the same value, only one computation is necessary, and a 30-second old value is allowed during refresh.

Reasoning: Coalescing concurrent misses turns 5,000 source queries into one refresh. Briefly serving the previous value keeps callers moving while that refresh finishes.

Boundary: Caching can protect the database during normal hits yet overload it at expiry. Expiry jitter, early refresh, and request coalescing must be explicit parts of the design.

17. Redundant application servers still have one entry-point failure
Current system
The public hostname points to one self-managed load-balancer virtual machine. That machine distributes requests across ten application servers in two availability zones.
Observed evidence
When the load-balancer machine is stopped, every application server remains healthy, but clients cannot reach any of them because the hostname still leads to the stopped machine.
Required behavior
Survive the loss of any one virtual machine without a manual DNS change and restore request routing within 60 seconds.
Known constraints
The platform offers a managed regional load-balancing service with multiple internal instances and health-aware routing. Alternatively, a self-managed pair would need a health-aware public failover mechanism.

Decision: What does “the load balancer also needs redundancy” mean in this exact system?

Given facts: Every client must pass through one load-balancer machine, its failure makes all healthy backends unreachable, and automatic recovery is required.

Reasoning: Redundancy must cover the entry path itself. Clients need a healthy balancing instance to be selected automatically; merely creating a second hidden instance does not make it reachable.

Boundary: Backend redundancy protects against backend failure. Balancer redundancy protects the route to those backends. Each layer must avoid becoming the next single point of failure.

18. Fast queue intake hides slow business completion
Current system
API producers durably enqueue 500 image jobs per second in about 30 milliseconds. Consumers collectively finish only 400 jobs per second.
Observed evidence
The oldest pending job has grown from 10 seconds old to two hours old. The difference of 100 jobs per second has accumulated roughly 720,000 pending jobs in two hours.
Required behavior
Continue accepting jobs only while 95% can finish within five minutes. Accepted jobs must not be silently discarded.
Known constraints
Consumer capacity can be increased. Producers can receive a temporary “try later” response if the system cannot honor the completion target.

Decision: Which operational conclusion follows from the written rates and end-to-end requirement?

Given facts: Work arrives 100 jobs per second faster than it finishes, pending age is two hours, and the required completion time is five minutes.

Reasoning: A queue can absorb a temporary burst, but a sustained rate deficit grows forever. Consumer throughput must exceed arrivals long enough to drain the backlog; intake may need limiting while it recovers.

Boundary: Fast enqueue latency proves only that intake is responsive. It does not prove that the promised business result is available on time.

19. One checkout flow contains four different timing and correctness contracts
Current system
Checkout synchronously reads catalog details, reserves inventory, sends a receipt email, and scans the day’s orders for analytics before returning success.
Observed evidence
The response takes 3.8 seconds. Catalog reads repeat heavily, email takes about one second, and the analytics scan grows throughout the day.
Required behavior
Confirm checkout within 500 milliseconds only after inventory is durably reserved. Send email within five minutes after that commit. Publish complete analytics by 6:00 AM next day.
Known constraints
Catalog data may be 30 seconds stale. Inventory must not oversell and must have a failover copy. Duplicate receipt emails are not allowed.

Decision: Which decomposition respects every stated contract rather than forcing all work onto one request path?

Given facts: Catalog permits bounded staleness, inventory requires a durable synchronous decision and failover copy, email has a five-minute window with no duplicates, and analytics is due next morning.

Reasoning: Each mechanism matches one contract: cache repeated tolerant reads, replicate the authoritative inventory path, queue post-commit email with deduplication, and batch deadline-based analytics.

Boundary: “Asynchronous” must not move the correctness point. Checkout can return only after inventory commits; queue acceptance proves email work was accepted, not that inventory was reserved.

20. Select an optimization from a measured latency trace
Current system
A JSON product-search API takes 800 milliseconds: 520 milliseconds in one database scan, 180 milliseconds in application code, and 100 milliseconds in network travel.
Observed evidence
The database scans 20 million rows to return 20 rows because the filter has no index. Only 2% of API requests repeat, and application CPU is 25%.
Required behavior
Reduce the API to below 400 milliseconds while returning the latest database state.
Known constraints
Static files already use a content delivery network (CDN); the 800 milliseconds is only the API call. Users are near the server region. Code moved to an edge location would still call the same central database.

Decision: Which first experiment attacks the largest measured cost and can plausibly meet the target?

Given facts: The unindexed scan consumes 520 of 800 milliseconds, the target requires saving more than 400 milliseconds, reuse is only 2%, and distance is not dominant.

Reasoning: An appropriate index lets the database locate the 20 matching rows without scanning 20 million. It targets the only measured cost large enough to meet the goal by itself.

Boundary: A CDN serves reusable content near users. Edge computing runs code near users. Neither removes a central database scan when the request still requires the newest central state.
