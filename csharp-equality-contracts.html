Learning checkpoint 1 of 10

First choose the question: identity or value?

Many equality mistakes happen because the program asks one question while the developer mentally answers the other.

Identity / reference equality

“Is this the exact same object?”

Two variables have reference equality when both references lead to one object. The object’s property values do not decide the answer.

Value equality / equivalence

“Should these represent the same value?”

Two separate objects can be value-equal when the type’s chosen data matches. The type author defines which data matters.

Identity: first and alias are the same object; first and separate are not. Value: whether A and B are equal depends on the equality policy of User.

A plain class starts with identity-based equality

public sealed class User
{
    public string Name { get; }

    public User(string name) => Name = name;
}

var first = new User("Maya");
var alias = first;
var separate = new User("Maya");

Console.WriteLine(ReferenceEquals(first, alias));    // True
Console.WriteLine(ReferenceEquals(first, separate)); // False
Console.WriteLine(first == separate);                // False
Console.WriteLine(first.Equals(separate));           // False

Why: this class has not defined value equality or overloaded ==. Matching Name values do not automatically change the inherited identity behavior.

Learning checkpoint 2 of 10

C# gives you five related equality tools

They overlap, but they are not interchangeable. Start by knowing the question and dispatch rule of each tool.

Tool What it asks Important boundary
ReferenceEquals(a, b) Do both references identify the same object? Cannot be overridden. Value-type arguments are boxed, so it is the wrong tool for comparing values.
a == b Run the equality operator selected from the operands’ compile-time types. A plain class uses reference equality; a type may overload the operator. string and records provide value-based operators.
a.Equals(b) Ask the runtime object referenced by a whether it equals b. Virtual dispatch can reach an override. Calling it when a is null throws NullReferenceException.
object.Equals(a, b) Perform a null-safe equality check, then delegate to a.Equals(b). Both null is true; exactly one null is false. This is not the same as forcing reference equality.
EqualityComparer<T>.Default.Equals(a, b) Use the default typed equality policy for T. Generic collections use this pattern. It prefers IEquatable<T> when the type implements it.

Null-safe versus instance call

User? left = null;
User? right = null;

Console.WriteLine(object.Equals(left, right));    // True
Console.WriteLine(ReferenceEquals(left, right));  // True
Console.WriteLine(left is null);                  // True

// left.Equals(right) would throw:
// left does not reference an object to receive the call.

Syntax note: User? says the reference is allowed to be null. Nullable reference types are a later topic; that one reading is enough for this page.

Use is null inside an overloaded operator

A type can overload ==, so left == null may call your operator again and recurse. The pattern left is null performs a null test without invoking an overloaded equality operator.

Learning checkpoint 3 of 10

For ==, compile-time types choose the operator

This is the most important prediction rule in the topic. The same two runtime objects can produce different == results after their references are stored in variables of another static type.

1 · Read static types

Look at the declared types of the two operand expressions.

2 · Select operator

The compiler binds an available == operator for those types.

3 · Run it

The selected operator executes; ordinary == is not a virtual method call.

One pair of strings, three different questions

string left = new string(new[] { 'h', 'i' });
string right = new string(new[] { 'h', 'i' });

object leftAsObject = left;
object rightAsObject = right;

Console.WriteLine(left == right);                    // True
Console.WriteLine(leftAsObject == rightAsObject);    // False
Console.WriteLine(leftAsObject.Equals(rightAsObject)); // True
Console.WriteLine(ReferenceEquals(left, right));     // False
Line 1: both operands are statically string, so the value-based string operator runs.
Line 2: both operands are statically object, so object == object compares references.
Line 3: Equals is virtual, so the runtime string override compares text.
Line 4: the two separately created string objects have different identities.
Expression Selection time Can runtime type change the implementation?
a == b Compile time, from operand types and available operators Normally no. The compiler has already selected a static operator.
a.Equals(b) The method signature is checked at compile time Yes. Virtual dispatch selects the override of the runtime object referenced by a.
ReferenceEquals(a, b) Fixed static method No. It always tests object identity and cannot be overridden.
Learning checkpoint 4 of 10

A valid equality implementation obeys laws

The code is correct only if callers can safely reason about its results. These laws are the reusable test checklist.

Reflexive

Every non-null value equals itself.

x.Equals(x) == true
Symmetric

Neither operand gets a privileged answer.

x.Equals(y) == y.Equals(x)
Transitive

A chain of equality cannot contradict itself.

x=y and y=z ⇒ x=z
Consistent

Repeated checks agree while equality-relevant state is unchanged.

same state ⇒ same answer
Non-null

A real instance is not equal to null.

x.Equals(null) == false
Hash consistent

Equal values must produce the same hash code.

x=y ⇒ hash(x)=hash(y)

Inheritance can break symmetry

If a base class compares only base fields but a derived class also compares a new field, the base object may accept the derived object while the derived object rejects the base object.

public class Point
{
    public int X { get; }
    public int Y { get; }

    public Point(int x, int y) => (X, Y) = (x, y);

    public override bool Equals(object? obj) =>
        obj is Point other && X == other.X && Y == other.Y;

    public override int GetHashCode() => HashCode.Combine(X, Y);
}

public sealed class ColoredPoint : Point
{
    public string Color { get; }

    public ColoredPoint(int x, int y, string color) : base(x, y) =>
        Color = color;

    public override bool Equals(object? obj) =>
        obj is ColoredPoint other &&
        base.Equals(other) &&
        Color == other.Color;

    public override int GetHashCode() =>
        HashCode.Combine(base.GetHashCode(), Color);
}

Point plain = new Point(1, 2);
Point colored = new ColoredPoint(1, 2, "Red");

Console.WriteLine(plain.Equals(colored)); // True
Console.WriteLine(colored.Equals(plain)); // False — broken symmetry

Safe default: make a value-like custom class sealed. If it must support inheritance, define and test an exact runtime-type policy deliberately. Records generate an equality type boundary for record inheritance.

Learning checkpoint 5 of 10

Implement one source of truth, then connect every entry point

This complete value-object class compares an amount and a normalized currency code. Study the direction of delegation.

Complete custom equality for a sealed class

#nullable enable
using System;

public sealed class Money : IEquatable<Money>
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency)
    {
        if (string.IsNullOrWhiteSpace(currency))
        {
            throw new ArgumentException(
                "Currency is required.", nameof(currency));
        }

        Amount = amount;
        Currency = currency.Trim().ToUpperInvariant();
    }

    // The typed method is the single source of equality truth.
    public bool Equals(Money? other) =>
        other is not null &&
        Amount == other.Amount &&
        Currency == other.Currency;

    // Object-based callers delegate to the typed method.
    public override bool Equals(object? obj) =>
        obj is Money other && Equals(other);

    // Use exactly the same equality-relevant data.
    public override int GetHashCode() =>
        HashCode.Combine(Amount, Currency);

    // Operators follow the same policy and handle null safely.
    public static bool operator ==(Money? left, Money? right) =>
        ReferenceEquals(left, right) ||
        (left is not null && left.Equals(right));

    public static bool operator !=(Money? left, Money? right) =>
        !(left == right);
}

Why sealed?

No derived type can add new equality-relevant state and create the base/derived symmetry problem shown earlier.

Why normalize currency?

"usd" and "USD" become one representation. Equality and hashing then use the same simple value.

Why check identity first?

If both operands are the same reference—including both null—the answer is immediately true. Otherwise the typed equality method decides.

The delegation direction

Equals(Money?) contains the real field comparison. Equals(object?) validates the type and delegates. == handles identity/null and delegates. != negates ==. GetHashCode uses the same fields. One policy, five consistent entry points.

Learning checkpoint 6 of 10

IEquatable<T> is intrinsic; IEqualityComparer<T> is contextual

The angle-bracket T is a type placeholder. For IEquatable<Money>, the placeholder is replaced with Money.

Inside the type

IEquatable<T>

The type declares its natural, reusable meaning of equality through bool Equals(T other). Generic collections can call the typed method directly. For value types, this also avoids boxing during typed comparisons.

Supplied by a caller

IEqualityComparer<T>

An external object supplies Equals(T, T) and GetHashCode(T) for a particular context. It lets two collections use different valid policies without changing the type.

Collection has T

For example, HashSet<Money> knows its element type.

Default comparer

EqualityComparer<T>.Default selects the type’s default policy.

Typed equality

If T implements IEquatable<T>, that typed implementation is used.

Context-specific equality without changing string

using System;
using System.Collections.Generic;

var exact = new HashSet<string>();
exact.Add("admin");

var usernames =
    new HashSet<string>(StringComparer.OrdinalIgnoreCase);
usernames.Add("admin");

Console.WriteLine(exact.Contains("ADMIN"));     // False
Console.WriteLine(usernames.Contains("ADMIN")); // True

Decision rule: put equality inside the type when it is the type’s stable natural meaning. Pass an external comparer when the policy belongs to one operation or collection.

Do not implement only the typed method and forget object.Equals

Some callers hold a value as object; others use generic APIs. Keep both paths consistent by overriding Equals(object?) and delegating it to Equals(T?). If you define equality, also provide the matching GetHashCode.

Learning checkpoint 7 of 10

A hash code chooses candidates; Equals confirms

A hash code is not a unique ID and does not prove equality. It helps a hash-based collection avoid comparing the new key with every existing key.

1 · Compute hash

The collection asks its comparer for the key’s integer hash code.

2 · Choose bucket

The hash narrows the search to a smaller group of candidate keys.

3 · Confirm equality

The comparer calls equality on candidates because different values may share one hash.

Required implication
If x.Equals(y) is true, then x.GetHashCode() == y.GetHashCode() must be true.
Not a valid reverse implication
If two hash codes match, the objects may still be unequal. This ordinary situation is a hash collision.

Broken contract: equality uses Id, hashing uses Name

// Deliberately wrong — do not copy.
public bool Equals(Customer? other) =>
    other is not null && Id == other.Id;

public override int GetHashCode() =>
    Name.GetHashCode();

Two customers with the same Id but different names are declared equal, yet can be routed to different buckets. A HashSet<Customer> or Dictionary<Customer, ...> can then fail to find an equal candidate.

// Correct: use the same equality-relevant data.
public override int GetHashCode() => Id.GetHashCode();

A good hash implementation

  • Uses every field that participates in equality, in a compatible way.
  • Returns the same value while equality-relevant state is unchanged.
  • Distributes ordinary values reasonably; collisions remain allowed.
  • Can use HashCode.Combine(a, b, ...) for multiple fields.

A hash code is not

  • A globally unique identifier.
  • Proof that two values are equal.
  • A security hash or encryption mechanism.
  • A value you should persist or transmit; it is not guaranteed stable across processes or runtime versions.
Learning checkpoint 8 of 10

Hash keys need stable equality-relevant state

A collection remembers where it placed a key using the hash computed at insertion. Mutating a field used by equality and hashing can make the stored key unreachable through normal lookup.

The mutable-key failure

public sealed class MutableKey : IEquatable<MutableKey>
{
    public int Id { get; set; }

    public bool Equals(MutableKey? other) =>
        other is not null && Id == other.Id;

    public override bool Equals(object? obj) =>
        obj is MutableKey other && Equals(other);

    public override int GetHashCode() => Id.GetHashCode();
}

var key = new MutableKey { Id = 10 };
var set = new HashSet<MutableKey> { key };

key.Id = 99; // The object is still stored under the old hash path.

bool found = set.Contains(key); // Lookup behavior is now unreliable.

Mechanism: insertion used the hash for 10; lookup now starts from the hash for 99. The collection does not automatically move the existing entry when a property changes.

Best fix

Make equality-relevant properties read-only after construction. Immutable value objects are naturally safe keys.

Alternative

Remove the key before changing it, mutate it, and add it again. This is easy to misuse and is usually less robust.

Another design

Use an immutable stable identifier—such as an integer or string ID—as the dictionary key instead of the mutable object.

init and get-only properties are not automatically deep immutability

They stop a property reference from being replaced after initialization, but a referenced mutable object—such as a List<T>—can still change internally. Deep immutability requires every reachable equality-relevant value to be immutable or protected.

Learning checkpoint 9 of 10

Records generate value equality—but not deep equality

A record is ideal when the object primarily represents a bundle of values. The compiler generates the routine equality members, but each member still follows its own equality behavior.

The compact record version of a value object

public sealed record MoneyRecord(decimal Amount, string Currency);

var first = new MoneyRecord(10m, "USD");
var second = new MoneyRecord(10m, "USD");

Console.WriteLine(ReferenceEquals(first, second)); // False
Console.WriteLine(first == second);                // True
Console.WriteLine(first.Equals(second));           // True
Console.WriteLine(first.GetHashCode() ==
                  second.GetHashCode());           // True

The compiler provides value-based Equals, IEquatable<MoneyRecord>, compatible GetHashCode, ==/!=, and a readable ToString. Positional record properties use init by default.

Type choice Default equality Typical use
Plain class Reference identity unless you override/overload Services, mutable objects, or entities where object identity is meaningful
Sealed class with custom equality Your explicitly implemented policy Value objects needing validation, normalization, or a specialized equality rule
record class Generated value equality; still a reference type Data-centric values, messages, immutable-style models, configuration snapshots
readonly record struct Generated value equality; copied as a value type Small immutable values when value-type copying is appropriate

Two record traps you must know

Trap 1 · with is a shallow copy

public sealed record Order(
    string Number,
    List<string> Items);

var original = new Order(
    "A-1",
    new List<string> { "Keyboard" });

var copy = original with { Number = "B-1" };
copy.Items.Add("Mouse");

Console.WriteLine(original.Items.Count); // 2
Console.WriteLine(
    ReferenceEquals(original.Items, copy.Items)); // True

The record object is new, but both Items properties hold a copy of the same list reference.

Trap 2 · Member equality can be reference equality

public sealed record Packet(byte[] Data);

var first = new Packet(new byte[] { 1, 2 });
var second = new Packet(new byte[] { 1, 2 });

Console.WriteLine(first == second); // False

The two arrays contain equal bytes, but arrays use reference equality for Equals. Generated record equality delegates to the member type’s equality; it does not automatically compare collection elements.

Original record

Number = "A-1"

Items → shared List object
→
New outer record

Number = "B-1"

Items → same List object

Record inheritance has an equality type boundary

Generated record equality checks the runtime record type through an equality contract, so a base record and a derived record do not become equal merely because their base data matches. This protects symmetry. It does not make ordinary custom class inheritance automatically safe.

Learning checkpoint 10 of 10

Choose semantics before choosing syntax

Do not start with “Should I override Equals?” Start with “What real-world fact makes two instances interchangeable in this domain?”

Entity: continuity through change

A customer can change name and address but remain the same customer.

  • Use a stable identity such as CustomerId.
  • Do not include mutable descriptive fields in equality or hashing.
  • A class with ID-based custom equality—or reference identity inside one unit of work—may fit.

Value object: meaning is its data

Money(10, "USD") is interchangeable with another value carrying the same normalized amount and currency.

  • Include all data that determines the value.
  • Keep that data immutable.
  • A record or sealed class with custom value equality usually fits.

Interview edges worth remembering

string

It is a reference type, but string == string and string.Equals compare text values. As seen earlier, casting both operands to object changes which == operator is selected.

Arrays and ordinary lists

Their default object equality is reference-based. Equal elements do not make two separate arrays equal. Element-by-element comparison needs an explicit operation such as LINQ’s SequenceEqual.

Floating-point NaN

For two double.NaN variables, x == y is false while x.Equals(y) is true. Built-in numeric contracts can contain deliberate edge behavior.

Value types and identity

ReferenceEquals(10, 10) is false because each value argument is boxed separately. Use value equality for value types, not object identity.

Null pair

object.Equals(null, null) and ReferenceEquals(null, null) are true. An instance call such as left.Equals(right) cannot run when left is null.

Hash collisions

Different values may share a hash code. A correct dictionary still distinguishes them by running equality among candidates in the bucket.

60-second interview answer C# equality can mean identity or value equivalence. ReferenceEquals always checks identity. The == operator is selected at compile time from the operands’ static types, while an overridden instance Equals uses virtual dispatch. A value-like custom type should keep typed IEquatable<T>.Equals, Equals(object), optional ==/!=, and GetHashCode consistent. Equality must be reflexive, symmetric, transitive, stable, null-safe, and hash-consistent. Hash collections compute a hash to find candidates and then call equality, so equal objects need the same stable hash and mutable equality fields make dangerous keys. Records generate value equality and shallow with copies, but nested reference members still use their own equality.

Exercise 1 of 10

Predict identity for a plain class

Foundation

Predict all three lines. Ticket does not override equality or overload operators.

var first = new Ticket(7);
var alias = first;
var separate = new Ticket(7);

Console.WriteLine(first == alias);
Console.WriteLine(first == separate);
Console.WriteLine(first.Equals(separate));
Hint

Matching property values do not automatically create value equality for a plain class.

Solution

True, False, False. first and alias point to one object. separate is a different object, and the class inherits identity-based object.Equals.

Exercise 2 of 10

Follow the static types

Foundation

Predict the three results and name the mechanism responsible for each.

string a = new string(new[] { 'o', 'k' });
string b = new string(new[] { 'o', 'k' });
object x = a;
object y = b;

Console.WriteLine(a == b);
Console.WriteLine(x == y);
Console.WriteLine(object.Equals(x, y));
Hint

The first two lines contain different compile-time operand types. The third call is null-safe and delegates to the left runtime object’s virtual equality.

Solution

True, False, True. string == string compares text. object == object compares references. object.Equals(x, y) delegates to the runtime string’s value-based override.

Exercise 3 of 10

Make the null behavior explicit

Foundation

Assume Customer is a plain class. Which expressions return true, which return false, and which throw?

Customer? a = null;
Customer? b = null;

object.Equals(a, b)
ReferenceEquals(a, b)
a == b
a is null
a.Equals(b)
Hint

Four expressions can evaluate without dereferencing a. The final expression requires an object to receive an instance method call.

Solution

The first four expressions are true. Both operands are null, and the plain class operator treats the references as equal. a.Equals(b) throws NullReferenceException because a has no object.

Exercise 4 of 10

Catch a built-in edge case

Foundation

Predict both results. Then explain why “== and Equals always agree” is not a safe universal rule.

double x = double.NaN;
double y = double.NaN;

Console.WriteLine(x == y);
Console.WriteLine(x.Equals(y));
Hint

IEEE floating-point operator semantics and .NET’s typed Double.Equals contract intentionally answer this edge case differently.

Solution

False, True. The floating-point == operator treats NaN as unequal to every value, including NaN. Double.Equals treats two NaN values as equal, which allows typed equality-based collections to handle NaN consistently.

Exercise 5 of 10

Implement a coordinate value object

Implementation

Create a sealed Coordinate class whose equality uses X and Y. Implement typed equality, object equality, hash code, and both equality operators.

Hint

Use Equals(Coordinate?) as the single field-comparison source. Use HashCode.Combine(X, Y). Inside ==, use ReferenceEquals and is not null.

Solution 
#nullable enable
using System;

public sealed class Coordinate : IEquatable<Coordinate>
{
    public int X { get; }
    public int Y { get; }

    public Coordinate(int x, int y) => (X, Y) = (x, y);

    public bool Equals(Coordinate? other) =>
        other is not null && X == other.X && Y == other.Y;

    public override bool Equals(object? obj) =>
        obj is Coordinate other && Equals(other);

    public override int GetHashCode() => HashCode.Combine(X, Y);

    public static bool operator ==(
        Coordinate? left, Coordinate? right) =>
        ReferenceEquals(left, right) ||
        (left is not null && left.Equals(right));

    public static bool operator !=(
        Coordinate? left, Coordinate? right) =>
        !(left == right);
}

Exercise 6 of 10

Repair a broken hash contract

Implementation

This type declares products equal by Sku, ignoring case, but its hash code is wrong in two ways. Find both and repair it.

public bool Equals(Product? other) =>
    other is not null &&
    StringComparer.OrdinalIgnoreCase.Equals(Sku, other.Sku);

public override int GetHashCode() =>
    Name.GetHashCode();
Hint

The hash must use the same property and the same case-insensitive policy as equality.

Solution 
public override int GetHashCode() =>
    StringComparer.OrdinalIgnoreCase.GetHashCode(Sku);

The original used Name instead of Sku, and ordinary string hashing did not match the case-insensitive equality policy. The comparer provides compatible equality and hashing.

Exercise 7 of 10

Diagnose the disappearing-key bug

Debugging

A Session uses mutable Token for equality and hashing. It is inserted into a dictionary and then its token changes. Explain why lookup can fail and give two safer designs.

Hint

Ask which hash chose the insertion bucket and which hash chooses the later lookup bucket.

Solution

The entry remains stored through the old token’s hash path, while lookup begins through the new token’s hash path. The dictionary does not observe property changes and re-bucket the key.

Safer designs: make Token immutable, or use the immutable token string itself as the dictionary key. A more fragile alternative is remove → mutate → add.

Exercise 8 of 10

Trace a record’s shallow copy and equality

Debugging

Predict all three results after the mutation.

public sealed record Cart(List<string> Items);

var first = new Cart(new List<string> { "Book" });
var copy = first with { };

copy.Items.Add("Pen");

Console.WriteLine(ReferenceEquals(first, copy));
Console.WriteLine(ReferenceEquals(first.Items, copy.Items));
Console.WriteLine(first == copy);
Hint

with creates a new outer record but copies the list reference. Record equality compares the list member using the list’s own equality.

Solution

Exercise 9 of 10

Choose an external equality policy

Design

A login service must treat "Ram", "ram", and "RAM" as one username inside a set. You must not change string itself. Choose and show the collection configuration.

Hint

The policy belongs to this collection context, so pass an IEqualityComparer<string> implementation to the constructor.

Solution 
var usernames =
    new HashSet<string>(StringComparer.OrdinalIgnoreCase);

Console.WriteLine(usernames.Add("Ram")); // True
Console.WriteLine(usernames.Add("RAM")); // False
Console.WriteLine(usernames.Count);      // 1

StringComparer.OrdinalIgnoreCase supplies matching case-insensitive equality and hashing. “Ordinal” makes this an identifier comparison, not a culture-sensitive linguistic comparison.

Exercise 10 of 10

Design and test entity equality

Interview

A subscription keeps the same immutable SubscriptionId when its plan name changes. Define the equality policy, name the fields used by GetHashCode, and list five tests you would run.

Hint

This is an entity: continuity comes from a stable ID, not from all current descriptive properties. Use the equality laws as the test plan.

Solution

Policy: two subscriptions are equal when their immutable SubscriptionId values are equal. Changing PlanName must not affect equality. GetHashCode must use only SubscriptionId.

Tests: (1) one instance equals itself; (2) two instances with the same ID are symmetric; (3) three instances sharing an ID are transitive; (4) equal instances have equal hash codes; (5) an instance is unequal to null and to a different ID. Also verify changing PlanName leaves equality and hash code unchanged.

var a = new Subscription(42, "Basic");
var b = new Subscription(42, "Premium");
var c = new Subscription(42, "Team");

Assert(a.Equals(a));                       // Reflexive
Assert(a.Equals(b) == b.Equals(a));        // Symmetric
Assert(a.Equals(b) && b.Equals(c) &&
       a.Equals(c));                       // Transitive
Assert(a.GetHashCode() == b.GetHashCode());// Hash consistent
Assert(!a.Equals(null));                   // Non-null
